# Independent email/password accounts
The /login route implements account creation, login, email verification, resend, forgotten-password recovery and password update through the official Supabase SSR SDK. Passwords are handled by Supabase; they are never stored in D1, R2, source code or logs. Username is a display name; email is the login identifier. Weekly-email opt-in is optional and no newsletter delivery is active.

Required runtime values: SUPABASE_URL and SUPABASE_PUBLISHABLE_KEY (public project key, never service_role). For standalone hosting set AUTH_MODE=supabase; missing configuration must fail closed. Enable email confirmation, use a verified SMTP sender, configure rate limits / bot protection as appropriate, and allow exact production and development callback URLs. Set Site URL to the public origin. Add /auth/confirm to allowed redirects. Recovery returns to /auth/confirm?next=/login?mode=update. For cross-device token-hash templates use /auth/confirm?token_hash={{ .TokenHash }}&type=signup (or recovery); retain the default PKCE code flow when using same-browser verification.

Authentication settings are not configured in this checkout. The form deliberately blocks submission until configured. Live signup/reset delivery must be tested with the actual provider before public release.

When email auth is enabled, all API routes verify Supabase identity and ignore Sites identity headers. The verified bootstrap owner email maps to the existing owner ID to preserve that account's cellar and admin role. Other pre-existing members require a reviewed identity mapping before migration; never map unverified email or user-supplied headers to existing owners. Do not copy deployment-local test records into production.

Contact email is independently editable in profile settings and is private. It does not authenticate a member or grant admin rights. Sign-in email changes use the provider's verification flow; require Secure Email Change (confirmation of both old and new addresses). Configure the email_change callback template when using token hashes. The verified owner's provider ID is bound in private R2 so future email changes retain the same cellar and admin identity. A different provider ID cannot reclaim that binding by taking the old email address.

ALEX B uses the same password and verified-email gate as every member. Admin is an authorization role, not a sign-in bypass. Do not enable public registration until real signup, verification, recovery and email delivery have been checked. Supabase can provide authentication while Sites continues to host the existing database and photo storage; no personal Cloudflare account is needed for that setup.


## Temporary launch without email verification (2026-10-13)
Set EMAIL_VERIFICATION_REQUIRED=false in Sites and disable Confirm email in Supabase after deploying the protected owner-binding code. Signup keeps username/email/password and redirects only when Supabase returns a session. Reset/resend/sign-in email changes are unavailable while mail is down. Newsletter UI is removed; saved consent data is preserved. New accounts carry email_verification_deferred=true in provider metadata; do not treat auto-confirmation as mailbox ownership. Before restoring email confirmation, design an explicit verification flow for these accounts; toggling Confirm email alone does not retroactively verify them.

Owner privileges use ADMIN_SUPABASE_USER_ID pinned by the operator to the owner's actual Auth UUID, never a submitted email or username. Existing owner bindings remain stable. Verify the human owner's registration before setting this variable. Existing Sites DB/R2 resources are unchanged.
